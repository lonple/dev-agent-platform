# 初审相关需求规格（讨论记录）

记录产品经理初审、AI 初审已确认的业务逻辑。口语化记录，不定实现细节。

---

## 产品经理初审

- 在自动化流水线里，这一步**默认直接通过**，不停留等人点确认。
- 时间线上还是可以看见这个节点，方便追溯。
- 真要挡人的产品关卡，用后面的二审之类，不靠这道初审。

---

## AI 初审（整体）

- 不再单独做「初审有效确认」节点。
- AI 初审里拆成**两个 Agent 任务单元**：
  - 业务评审：产品经理岗位触发，AI 产品经理，用《原始需求评估模板-业务》
  - 技术评审：架构师岗位触发，AI 架构师，用《原始需求评估模板-技术》
- 两个单元都按下面「单 Agent 两段式」跑完（各自确认 + 各自写出评审书）之后，AI 初审才算过；需要的话再汇总一份总的初审评审书（可选）。
- 产品经理和架构师如果是**同一个人（兼岗）**：节点基本信息里仍然展示**两个任务单元**，两个都能触发、都能确认。
- 只有**本岗**能触发本单元的 Agent、能提交本单元确认；其他岗位可以看，不能触发、不能确认。

---

## 评审 Agent：确认循环（业务 / 技术都一样）

不是「问一轮就写书」，而是**循环**，直到 AI 不再有不确定项（或触达轮次上限，上限另定）。

```text
执行 Agent
  → 吐确认 JSON（findings + openQuestions）
  → 有待确认？ → 暂停 → 人确认 → 回灌
       → 本轮「问题 + 人确认」归档进 Wiki
       → AI 继续：若还有不确定 → 再吐 JSON → 再确认（第 2、3… 轮）
       → 直到 phase=ok（或等价：无需再确认）
  → 按模板写正式评审书 → 也归档到 Wiki
```

### 每一轮确认 JSON

- 靠**提示词约定**，不是模板里开「疑似问题」栏。
- 两类：
  - **一类 findings**：AI 认定有问题/风险，带建议和推荐 → 人「同意采纳推荐」或「不同意并写意见」
  - **二类 openQuestions**：AI 不确定 → 人必须解答
- `need_human_confirm` → 任务暂停，**本轮还不能写正式评审书**。
- 人确认嵌在该任务单元里展开；提交后回灌 Agent。
- 顶栏「取消自动化」才整条取消；单元「不同意」≠ 取消流水线。

### 循环规则

- 人回复之后，AI **还可以再抛不确定项**，继续触发**下一轮确认**（二次、三次…）。
- 每一轮都要：AI 本轮问题（确认 JSON）+ 人的确认结果 → **都归档到 Wiki**（见下路径）。
- 直到 AI 表示没有新的待确认项，才进入「按模板写评审书」。
- **本岗提交问题确认后，自动继续执行写文档**（各 Agent 单元均如此，无需再点「继续写 / 执行」）。
- 轮次上限、死循环怎么掐断：后面再定（先记需求：必须是可多轮循环）。

### 写正式评审书（循环结束后）

- 按对应评估模板写正文；模板里不要「业务风险 / 技术风险 / 疑似问题」待确认表。
- 多轮已确认内容消化进结论 / 前置条件；需要归档处置可用「已确认问题与处置」从各轮确认回填。

### Wiki 归档路径（每轮问题/确认 + 最终评审书）

统一落到：

```text
{产品编码}/{需求编号}/{文档名}.md
```

- 写在需求所属产品的 Wiki 下；缺目录按层级建。
- **每一轮**的「AI 提出的问题 + 人的确认」都要归档进 Wiki（同一路径约定；文档名可带轮次，如 `…-确认-r1.md`，或追加写入同一确认归档文档——实现时再选一种，需求上要求**每轮可追溯**）。
- **产品经理确认**（业务初审、生成需求分析等）与架构师确认一样，**确认内容必须进 Wiki**，不能只留在界面/会话里。
- 循环结束后的**正式评审书 / 产品需求说明书 md** 同样按该三级路径输出。
- 例：`ACCT/REQ-2026-001/原始需求业务评估-确认-r1.md`、`…/产品需求说明书-确认-r1.md`、`…/产品需求说明书.md`。

## 模板怎么改（已对齐）

- 《原始需求评估模板-业务》：去掉业务风险、疑似问题两节；留给循环结束后写价值/影响/结论。
- 《原始需求评估模板-技术》：去掉技术风险、疑似问题两节；留给循环结束后写可行性/影响/结论。
- 《评审模板》：同样思路，去掉疑似问题；确认后的正文用已确认问题与处置 + 结论。

不确定项、风险发现 → 全部走确认 JSON 循环；模板只负责循环结束后的正式文档结构。

## 交互相关（跟初审绑在一起的）

- 工作台点「自动化流水线」单开工作台（盖住需求详情），不是侧栏单独菜单。
- 能看任务流程时间线、当前流程基本信息。
- AI 节点可看执行过程；节点上可看首次提示词。
- 每个节点文档区分四块（分行文字链，不做成按钮方框）：
  - **输入文档** / **输出文档** / **提示词**：文字可点打开
  - **上下文**：只展示 Wiki **路径**；默认只显示 1 条，多条用 `…`，悬停看全部路径
- AI 初审任务单元：`执行 →（暂停 JSON → 展开确认 → 归档 → 可能再暂停）… → 写评审书并归档`。

## 生成需求分析（产品需求说明书）

- **输入文档**：原始需求；需求设计 PRD 模板
- **上下文**（只展示路径）：`wiki/{产品编码}/基线`；`{产品编码}/{需求编号}`
- **输出文档**：产品需求说明书（按 PRD 模板结构落入需求 Wiki）
- **执行 Agent 两段式**（与初审同思路）：
  - 有不确定 → **优先**只输出问题列表 JSON（findings / openQuestions）→ 暂停等**产品经理**确认（可多轮）
  - **产品经理的确认（问题 + 答复）必须写入 Wiki**，路径约定同初审：`{产品编码}/{需求编号}/产品需求说明书-确认-r{n}.md`（每轮可追溯）
  - 确认后且不再有问题时 → 再按模板输出《产品需求说明书》
  - 无不确定时可 `phase=ok`，跳过暂停直接写说明书
- 岗位：产品经理触发/确认；提示词在「提示词管理」按 `PM` + `GEN_PRD` 维护
- **说明书生成之后（分支）**：产品经理选择是否启动
  - **架构设计**（可选）
  - **UI 设计**（可选）
  - 勾选的启动对应节点；未勾选的**跳过**
- **架构设计完 + UI 设计完**（所选都完成后；若都跳过则设计侧视为齐）→ **一并触发**三类评审（并行，不是串完一个再开下一个）：
  - 需求设计 PRD 评审
  - 架构设计评审（仅当实际跑过架构设计；否则跳过）
  - UI 设计评审（仅当实际跑过 UI 设计；否则跳过）

### 生成架构设计（可选）

- **输入文档**：产品需求说明书；**架构设计文档模板**
- **上下文**（只展示路径）：`wiki/{产品编码}/架构设计`
- **输出**：架构设计文档（落入需求 Wiki）
- **两段式**（同需求分析）：
  - 有不确定 → 先输出问题列表 JSON → **架构师**确认；**问题 + 确认必须写入 Wiki**（如 `{产品}/{需求}/架构设计文档-确认-r{n}.md`）
  - 确认且无新问题后 → 再按模板输出《架构设计文档》

### 生成 UI 设计（可选）

- **输入文档**：产品需求说明书；**UI 设计规范**（产品级规范）
- **上下文**（只展示路径）：`wiki/{产品编码}/基线/UI设计`；`wiki/{产品编码}/基线/prd`
- **输出**：**HTML 的 UI 设计文档**（如 `{产品编码}/{需求编号}/UI设计.html`）
- **两段式**（同上）：确认归档后再输出 `UI设计.html`

### 三类评审（设计齐后并行）

共性：有不确定 → 问题 JSON → 本岗确认并**归档 Wiki** → 再输出本岗评审书（评审模板）。

#### 需求设计 PRD 评审

| 岗位 | 输入 | 上下文 | 代码仓库 |
|---|---|---|---|
| 研发 | 产品需求说明书、评审模板 | `wiki/{产品}/基线` | 有（仓库路径） |
| 测试 | 产品需求说明书、评审模板 | `wiki/{产品}/基线` | 无 |

#### 架构设计评审

| 岗位 | 输入 | 上下文 | 代码仓库 |
|---|---|---|---|
| 研发 | 产品需求说明书、架构设计文档、评审模板 | `wiki/{产品}/基线` | 有 |
| 测试 | 同上 | `wiki/{产品}/基线` | 无 |

#### UI 设计评审

| 岗位 | 输入 | 上下文 | 代码仓库 |
|---|---|---|---|
| 产品经理 | 产品需求说明书、UI设计.html、评审模板 | `wiki/{产品}/基线/产品` | 无 |
| 研发 | 同上 | `wiki/{产品}/基线` | 有 |
| 测试 | 同上 | `wiki/{产品}/基线` | 无 |

### 评审合并与文档修订（按轨独立，非三类齐后才合并）

**口径**：需求 / 架构 / UI **各自一条轨**，互不等待「全部结束」。

```text
某轨评审节点内，各岗 Agent 全部写完（该轨最后一名完成）
  → 立刻触发【该轨】合并确认（非独立时间线节点）
  → 【人确认】有价值项 → 生成该轨《合并评审》
  → 进入「文档修订」节点 · 本轨修订 Agent 任务单元
       → 【本岗再次确认】合并后的问题哪些要改（勾选）——在修订 Agent 环境内，执行前完成
            ├─ 本岗认为都不用改 / 无有效项 → 直接结束本修订 Agent（不执行改文档）
            └─ 本岗勾选了需改项 → 再执行本修订 Agent，按勾选项改文档并发布
另一轨可并行：本轨合并 → 文档修订里本岗确认 →（可选）执行本轨修订 Agent
全部「已启动轨」的修订任务都结束后
  → 同时进入详细设计 + 测试用例
```

| 评审轨 | 合并后进入 | 本岗再次确认（修订 Agent 内） | 岗位 / 任务类型 | 改什么 |
|---|---|---|---|---|
| 需求设计 PRD 评审 | 文档修订 · 修订需求分析 | 产品经理确认问题项后**自动执行修订** | `PM` / `REVISE_PRD` | 产品需求说明书 |
| 架构设计评审 | 文档修订 · 修订架构设计 | 架构师确认问题项后**自动执行修订** | `ARCH` / `REVISE_ARCH` | 架构设计文档 |
| UI 设计评审 | 文档修订 · 修订 UI 设计 | UI设计师确认问题项后**自动执行修订** | `UI` / `REVISE_UI` | UI设计.html |

未跑过的评审轨（跳过）→ 无该轨合并、无该轨修订任务。

要点：

- **不是**等 PRD+架构+UI 三类评审全部结束后再统一合并。
- 合并在评审收束时确认；**「是否修改」在「文档修订」节点、对应修订 Agent 任务单元里，由该修订岗位再次确认**。
- 任务单元交互：**一开始只有「确认问题项」** → 本岗勾选后点确认 → **自动执行修订**（无需再点一次执行）。
- 岗位：PRD → 产品经理；架构 → 架构师；UI → **UI 设计师**。
- 本岗认为都可以不改（或无有效合并项）→ **直接结束本修订 Agent**。
- 确认需改后自动修订：按勾选项改文档并发布（Wiki 升版；界面不强调版本号）。
- 所有已启动轨的修订任务都完成后，才进详细设计 + 测试用例。

### 详设 / 用例评审与修订（生成齐后）

**详设与测试用例都完成后**，**同时触发**（可并行）：

- **详细设计评审**（架构师、产品、测试）
- **测试用例评审**（架构师、产品、研发）

口径与设计侧评审轨相同（**按轨独立**）：

```text
本轨各岗评审 Agent 两段式写完
  → 立刻本轨合并确认（有价值）
  → 进入「文档修订（详设/用例）」节点 · 本轨修订 Agent
       → 本岗「确认问题项」→ 勾选需改 →「执行修订」→ 输出新版详设或用例
       → 或不需改直接结束本 Agent
「文档修订（详设/用例）」两个 Agent 都结束后
  → 按**详细设计**触发「开发编码」节点（`GEN_CODING`；同步写可自动化用例）
  → 「开发编码」完成后触发「集成测试」（`GEN_INT_TEST`：测试仓库 + 可自动化用例 →《集成测试报告》）
```

| 评审轨 | 岗位 | 合并后修订 | 修订岗位 / 任务类型 | 改什么 |
|---|---|---|---|---|
| 详细设计评审 | 架构、产品、测试 | 修订详细设计 | `DEV` / `REVISE_DETAIL` | 详细设计文档 |
| 测试用例评审 | 架构、产品、研发 | 修订测试用例 | `QA` / `REVISE_CASES` | 需求测试用例 |

#### 开发编码（详设/用例修订齐后）

| 项 | 内容 |
|---|---|
| 触发 | 「文档修订（详设/用例）」两 Agent 均完成后 |
| 依据 | **详细设计文档**（修订后的现行版） |
| 岗位 | 研发 `DEV` / `GEN_CODING` |
| **代码仓库** | **有**（业务/实现仓库，必填） |
| **输出** | **编码完成报告**（落入需求 Wiki） |
| 执行 | **两段式**：有不确定 → 先问题确认并归档 → 再改代码；**编码阶段同步编写可自动化测试用例**；完成后输出《编码完成报告》；确认提交后自动继续 |

#### 集成测试（开发编码完成后）

## 产品经理二审

- 入口：AI 初审两侧评审书都写完后进入（可选汇总总评审书不影响二审输入）。
- 页面要同时看到：
  - **业务评估评审书.md** + 业务侧结论
  - **技术评估评审书.md** + 技术侧结论
- **必填放行信息**（无论结论是否齐通过，通过前都要填）：
  - **发布版本**：从需求所属**产品已配置的版本号**里选择（不是手填）
  - **发布时间**：可带出版本上的计划发布时间，允许改
- **两个放行按钮**：
  - **通过**：二审通过，需求状态进入类似「**已入计划**」；自动化流水线在此**挂起**，不启动后续研发步骤
  - **通过并投入研发**：同样写入版本/时间并二审通过，需求进入「投入研发」，**继续启动下一步**（如生成需求分析）
- **通过判定**（先定这个口径）：
  - 业务：结论为「建议做」→ 业务通过
  - 技术：结论为「可做」→ 技术通过
  - 两边都通过 → 结论侧视为就绪，仍须选版本/时间后再点上述按钮之一
  - 否则 → 二审**暂定**；选完版本/时间后仍可用两个按钮放行
- 只有产品经理岗位能操作；架构师等可看文档与结论。
