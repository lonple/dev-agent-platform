## 0. 背景与目标

当前 DAP 已具备：**多租户 + Wiki/个人空间 + 会话化 Agent + 可配置自动化流水线主干 + Git worktree 编码隔离**。

企业级落地的主要差距不在「再堆一条主路径」，而在：

- 身份合规与审计
- 多机部署与共享存储
- Agent 权限与沙箱
- 上下文/Token/超时治理与指标
- 水平扩容
- **运行时资源隔离**（端口、库、Flyway）与 **对接环境**

本文整理已讨论结论与建议口径，作为后续详细设计与排期输入。

## 1. 租户切分策略

### 1.1 结论（建议默认）

**租户按「产品线 / 产品族群」划分**，而不是按大部门或子公司一刀切。

| 切法 | 适合 | 风险 |
|---|---|---|
| **产品线 / 产品族（推荐默认）** | Wiki、代码仓、流水线、提示词、规范天然同域 | 跨产品协作需显式共享机制 |
| 大部门 / 子公司 | 组织人事、预算、强合规边界清晰 | 一部多产品时 Wiki/仓/流水线混杂，权限难精细 |
| 全公司一个租户 | 小团队快速开箱 | 隔离、配额、审计难以规模化 |

### 1.2 组织与租户的关系

- **租户**：产品协作与数据隔离边界（Wiki / 仓 / 流水线 / 配额）。
- **组织（部门/子公司）**：通过 **SSO（单点登录）** 组映射解决成员来源、审批链、预算归属；**不替代**租户边界。
- **强监管子公司**：可采用「子公司 = 租户」，其下仍用「产品」做二级隔离；流水线与仓绑定继续按产品走。

### 1.3 术语：SSO（单点登录）

**SSO** = **Single Sign-On（单点登录）**。

员工用公司统一账号（如企业微信 / 钉钉 / 飞书 / AD / LDAP / 统一认证中心）**登录一次**即可进入 DAP，无需再单独维护一套平台用户名密码。

企业落地时 SSO 通常一并考虑：

| 配套能力 | 说明 |
|---|---|
| OIDC / OAuth2 | 现代 Web 单点登录常用协议 |
| 离职回收 | 公司侧账号停用后，平台侧同步失效 |
| 组 / 部门映射 | 把公司组织映射到租户成员、角色 |
| MFA（可选） | 高权限操作二次校验 |

本文出现「接 SSO」即指：**对接公司统一身份，而不是只靠 DAP 本地账号。**

### 1.4 跨产品复用

规范/模板跨产品线复用时，优先：

- 平台级公共库；或
- 只读共享租户 / 共享规范目录；

避免把多个产品线硬塞进同一租户。

## 2. LLM 读写权限与沙箱

### 2.1 现状

操作权限（菜单/按钮）是小权限。真正的风险面是 **LLM 工具链对文件与仓库的读写，以及仓内白名单进程的副作用**。

#### 2.1.1 材料可见性白名单

当前通过会话材料白名单约束「能看见什么」：

- 上下文（Wiki）
- 输入文档
- 模板 / 规范
- 代码仓库（业务仓 BIZ / 测试仓 TEST；部分评审节点可为 NONE）

材料白名单**不管**写盘与跑命令是否逃逸。

#### 2.1.2 本机进程与命令白名单（已落地）

DAP **不提供**任意 shell（无 `bash -c` / `cmd /c` 类通用工具）。会起本机进程的场景均为白名单，大致三类：

| 类别 | 入口 | 说明 |
|---|---|---|
| Agent `run_action` | `CodeRepoToolService` + `ProcessBuilder` | 会话绑定仓后由 Agent 调用；动作名白名单，禁止拼任意命令串 |
| 端口进程控制 | `PortProcessControl`（`stop_port`） | Windows：`netstat` + `taskkill`；非 Windows：`lsof` 等；只接受已校验端口/PID |
| 平台内部 | `GitWorktreeService`、`RipgrepSearchService` | worktree 相关 `git …`；仓内/材料检索 `rg`（失败则 Java 行扫描回退） |

`run_action` 白名单动作（完整名，勿斜杠拼接）：

| 类别 | 动作 |
|---|---|
| Git 探查 | `git_status` / `git_diff` / `git_log` |
| 构建 | `build` / `build_gradle` / `build_maven` / `build_vite` |
| 测试 | `test` / `test_gradle` / `test_maven` / `test_node` / `test_uv` |
| 启动 | `start_dev` / `start_gradle` / `start_maven` / `start_vite` / `start_uv` |
| 依赖/版本 | `mvn_validate` / `mvn_deps_tree` / `gradle_deps` / `tool_version` |
| 进程（偏登记表） | `stop_dev` / `list_processes`（停会话内登记进程，不起新 shell） |
| 端口 | `check_port` / `stop_port` |

`build` / `test` / `start_dev` 会按仓内 gradle / pom / package.json / pyproject 等**自动选型**。流水线 IT 等若跑构建/测试/启动，也走同一套白名单面，而非另开任意命令通道。

仓内文件工具（与执行并列）：`list_dir` / `read_file` / `write_file` / `delete_file` / `search_code`。路径须落在会话绑定的仓根下（`RepoPathSandbox` 等），写入另有内容/路径校验。

#### 2.1.3 风险结论（当前）

- **命令白名单**防的是「随便一条 shell」，必要且已落地。
- **当前最大越权面**仍是：
  1. **会话绑了哪些仓根、绑得有多宽** → `read` / `write` / `delete` 对该根下内容的实际能力；
  2. **白名单执行的真实副作用** → gradle/mvn/npm/uv 等插件与脚本、`start_*` 拉起的服务：可读环境、出网、写到仓外路径、占端口等——命令形态受控，**副作用未进沙箱**，仍是本机进程；
  3. 次要：`stop_port` 可按端口杀进程，不限于「本仓起的」；worktree 只缩小「改哪份代码」，**不等于**执行隔离。

一句话：**白名单管命令形态与材料可见性；绑错/绑宽仓 + 仓内读写 + 白名单进程副作用，才是现阶段主风险。** Docker/沙箱（见下）要补的正是这一层。

### 2.2 分层加固（建议顺序）

**阶段 A — 硬化 ACL（性价比高，先做）**

- 产出路径只写不读；仓按 BIZ/TEST；禁止路径穿越与 symlink 逃逸
- 按任务类型配置工具能力画像（禁用高危写 / 收紧可绑仓根 / 限制 `start_*` 与 `stop_port` 等）
- 会话级 allowlist **启动时冻结**，中途不可扩权
- 默认优先绑需求 worktree，避免直接绑本机主工作区整仓

**阶段 B — Docker / 沙箱执行面（企业级目标态）**

见 **§2.3**（讨论结论）。

原则：**材料白名单管可见性；命令白名单管可启动的形态；沙箱管即使工具用错也出不去；合主干与远端凭证不进沙箱。**

### 2.3 Docker 沙箱方案（讨论结论）

> 本机概要：`设计/Docker沙箱-本机落地设计.md`；详细设计（库表/API/时序/改造清单）：`设计/Docker沙箱-详细设计.md`（不含 CA/mTLS）。

#### 2.3.1 目标与边界

| 要解决 | 不在沙箱里做 |
|---|---|
| 构建/测试/启动等进程逃逸宿主机 | 任意开放 shell（仍用动作白名单） |
| 写盘越出本任务工作区 | 推远端凭证、合主干、发 Wiki 正式稿 |
| 多任务并行抢端口/依赖 | 用容器替代「需求分支」本身 |

**沙箱隔离执行面；Git 分支 + worktree 仍是变更载体。** 目标部署环境按 **Linux** 规划；Windows + Docker Desktop 仅作开发联调，不以之为生产行为基准。

#### 2.3.2 逻辑拓扑与组件

```text
dap-agent（LLM）
  → dap-server（名额、会话/Job、合并、Wiki；工具 API 门面）
      → SandboxManager 主控（无业务状态：路由、下发、汇聚节点健康）
          → 各宿主机 sandbox-client（节点代理）
               ├─ 本机 Docker 生命周期 / 挂载 / 健康与指标
               └─ 转发 → 容器内 code-tools（读写/搜/run_action/commit）
```

| 组件 | 跑在哪 | 职责 |
|---|---|---|
| **dap-agent** | 控制面 | 只调 dap-server 工具 API |
| **dap-server** | 控制面 | 产品资源池名额；会话/Job；工具门面（转发执行）；push/合并/Wiki；**不再本机 ProcessBuilder/Files 打仓** |
| **SandboxManager（主控）** | 控制面 | 对业务无状态；按 DAP 指定的 resource/节点下发；汇聚各 client 健康与「执行侧是否充足」；可独立部署 |
| **sandbox-client（节点代理）** | **目标宿主机** | 本机 Docker 创建/附着/销毁；健康检查与指标采集上报；将代码操作请求转到本机 code-tools（或一期 `docker exec`） |
| **code-tools** | **沙箱容器内**（推荐） | 无 LLM；list/read/write/search/run_action/commit；强制路径与命令白名单 |

**分工一句话：名额在 DAP；主控路由；client 落主机管 Docker 与监控；code-tools 在沙箱里干活。**

开源可借鉴 E2B Runtime、K8s/Nomad 等；产品池与会话语义在 DAP 自研。

#### 2.3.2a 产品资源池（一期落地口径）

不在「一用户一容器」上死磕；改为 **产品管理侧维护若干 Docker 资源，申请公用**：

```text
产品
  └─ 登记 N 个 Docker 资源（地址/能力标签/健康状态等）
        每个资源默认最多同时占用 3 个需求（可配置）
用户或流水线 → 向 DAP 申请名额 → 占用某资源 1 席 → 用完释放
```

| 规则 | 说明 |
|---|---|
| 谁维护资源列表 | 产品管理（DAP） |
| 谁申请 | 交互会话 / 流水线 Job 同一套名额模型 |
| 并发 | 单资源默认 ≤ 3 需求；总容量 ≈ N × 每资源上限 |
| 满了怎么办 | 试下一资源；都满则 DAP 侧排队或拒绝 |
| 同资源多需求 | 各挂各的 worktree；端口/schema 仍走租约，避免 `start_*` 互撞 |
| 释放 | 任务结束（commit 后可释 worktree）或会话过期；超时回收防占坑 |

隔离粒度：同一 Docker 上最多 3 个需求 **共宿**，靠目录/应用层隔离；比一任务一短命容器弱，但运维简单，且仍保留 Manager 执行面，便于以后收紧。

#### 2.3.3 镜像

```text
dap-sandbox-base          # OS、git、非 root、code-tools 运行时等
  └─ dap-sandbox-java|node|python …   # 按语言族叠 JDK/Maven/Gradle、Node、uv 等
```

先做好 **基础镜像**，再基于基础镜像构建各 code 运行镜像；工具链进镜像构建，不进每次容器现场安装。

#### 2.3.4 代码进容器：映射，不 copy

- **源码**：bind mount 本任务 worktree（与现有 `GitWorktreeService` 对齐）  
- **依赖缓存**：可映射宿主/共享的 m2、gradle、npm 等缓存目录，或强制指向内网仓库  
- **材料**：只读挂载或只读快照  

改完即在同一 worktree 上，停容器不丢文件；避免 copy 再回传与合并链路打架。

**权限**：容器非 root 用户须对挂载的 worktree（及所需 `.git` 路径）具备读写；与宿主写仓用户 **UID/权限对齐或启动前授权**。这是文件系统权限问题，**不是** git 账号问题；commit 作者名邮箱可注入，远端登录凭证默认不进容器。

#### 2.3.5 Git 与合并职责

| 动作 | 位置 |
|---|---|
| 创建需求分支 + worktree | 任务开始前，宿主/`GitWorktreeService`（分支前置） |
| status/diff/log、**commit** | 容器内 code-tools（只 commit 到当前 feat 分支；**不挂远端 credential**） |
| push（若需要）/ 合主干 / PR / Wiki | **dap-server 控制面** |

主路径：

```text
ensure worktree（分支已在）
  → DAP 申请产品 Docker 名额（满则排队/拒绝）→ 会话绑定 resourceId / client 基址
  → Manager 主控 → 目标机 sandbox-client：附着 worktree、确认执行侧充足
  → Agent → dap-server 工具门面 →（经 Manager 或直连该 client）→ code-tools
  → 任务结束：commit → 释 worktree → DAP 还名额 → client 卸载本次占用
  → 合并节点：控制面 merge/PR + Wiki
```

**任务结束后释放 worktree**：目录可删；名额归还后可申请任意空席资源并按分支重新加载。  
**任务进行中**：继续落在已占用资源/宿主机，避免漂移。一期可不做共享盘。

#### 2.3.6 DAP 名额 vs Manager 主控 vs sandbox-client

```text
DAP 申请名额（N × 每资源上限如 3）
  → 通过 → SandboxManager 主控(resourceId, worktree, …)
  → 路由到该资源所在宿主机的 sandbox-client
  → client：本机探针 + Docker/attach + 转发 code-tools
  → 会话/Job 结束 → DAP 释放名额并通知卸载
```

| 在 DAP | 在 Manager 主控 | 在 sandbox-client |
|---|---|---|
| 资源登记、名额、排队、过期对账 | 无业务占用表；按 resource 路由 | 本机 Docker 与指标 |
| 选有空席的资源 | 汇聚节点健康/是否充足 | 健康检查、资源探针上报 |
| 工具 API 门面（改远程调用） | 可汇聚转发或返回 client 地址给 server | 转发或 exec 到 code-tools |
| 会话/Job 驱动停止 | 不解释业务过期 | 执行 stop/卸载 |

#### 2.3.6a 多机如何调用：不是 Docker「跨宿主机互联」

写码场景 **不需要** 各宿主机容器组成统一 Docker 覆盖网络。跨机交互是 **服务调用**：

```text
dap-server →（内网 HTTP/gRPC）→ 目标宿主机 sandbox-client
                                    → 本机再转 code-tools
```

产品资源登记需含：`resourceId`、所在节点、`clientBaseUrl`（或由 Manager 持有节点表）、能力标签等。  
会话占用名额后绑定该基址；此后读写/执行都打到 **对应机器的 client**，与 DAP 是否与 Docker 同机无关。

对外暴露二选一（可并存）：

| 方式 | 说明 |
|---|---|
| **端口映射** | code-tools 映射到宿主机端口；通常仅 `127.0.0.1`，只给本机 client 访问 |
| **宿主机代理** | 只暴露 sandbox-client；由 client 再转容器（利于鉴权、TLS、多容器） |

**跨主机只应访问 client（或 Manager）**，不要让 dap-server 直打各容器随机端口（难管、难鉴权）。通信限内网 + Token/mTLS。

目标宿主机 **几乎必然要有节点侧服务（即 sandbox-client）**：健康检查、指标采集、本地 Docker 管控。仅靠中心「盲连远程 Docker API」也可以做，但不利于监控与权限边界；与「Manager 对业务无状态」不矛盾——有状态的是「这台机器」。

#### 2.3.6b sandbox-client 如何转到 code-tools

| 方式 | 做法 | 适用 |
|---|---|---|
| **A. 本机反向代理（推荐）** | 容器 `-p 127.0.0.1:91xx:8080`；client 查 `sandboxId→localBaseUrl` 后 HTTP 转发 | 有独立 code-tools 服务 |
| **B. 容器网络** | client 与容器同网，访问 `http://code-tools-<id>:8080` | 单机多容器 |
| **C. docker exec（一期可合并）** | 无常驻 code-tools；client 对本机容器 exec/对挂载目录 IO | 少一个容器内进程；client 更重 |

请求需带 `sandboxId`/`resourceId`、工作区路径、操作类型；client 负责选对容器，code-tools 负责在目录内执行。

**与 code-tools 能否合并：**  
- 可以 **一期用 C**，把「代码操作 API」做在 client 上（逻辑合并）。  
- **不要**把持有 Docker socket 的管理进程放进业务沙箱容器（隔离倒挂）。  
- 长期仍建议 **client 在宿主机、code-tools 在沙箱内**，权限分离。

#### 2.3.6c 从 dap-server 拆出的能力

落地沙箱时，须将当前 `CodeRepoToolService` 一类能力拆离本机执行：

| 迁出到 code-tools（经 client） | 留在 dap-server |
|---|---|
| list/read/write/delete/search | 会话绑仓/材料白名单、名额、选资源 |
| run_action（构建/测试/启动等） | 工具 API 门面（鉴权后转发） |
| 路径沙箱与命令白名单的 **强制执行** | worktree 创建编排；push/合并/Wiki |
| 容器内 git commit | Git 远端凭证与合主干 |

Agent 侧工具名可不变；server 从本地 IO 改为远程调用。白名单必须在 **执行端再强制一遍**，不能只信 server。

#### 2.3.6d 演进：内核级隔离

SandboxManager + client 宜做成 **多运行时门面**：一期 Docker 共宿；后续可加 Firecracker / Kata / gVisor / E2B Runtime 等适配器，DAP 名额与会话模型可保持。  
注意：强隔离后「一 Docker 挂 3 需求」往往改为「一需求一实例」，产品池上限语义要跟着调；对外仍是 create/attach/exec/stop。

#### 2.3.7 运行与 IT（Compose）

- **一份（或少数）Compose 模板**，不是一任务一份 YAML  
- 启动时用 **项目名 + 环境变量** 区分实例：`-p dap-{reqNo}`，注入端口、schema、对接地址等（来自资源租约，见 §7/§8）  
- 「一任务一」指 **一套运行中的 compose 项目实例**，测完销毁  

`start_*` / IT：端口与配置由租约注入；沙箱态停进程 = 停容器/容器内进程，不再用宿主机 `taskkill` 扫端口。

#### 2.3.8 网络安全基线

- **依赖**：DAP/Runner 侧本地或内网依赖仓库（及缓存）映射或代理进容器；构建配置指向内网，不靠随意公网拉包  
- **出站默认拒绝**，白名单仅：  
  - DAP 相关服务（如 dap-server、本任务租约内的 DB/Redis 等）  
  - 产品对接环境中声明的地址  
  - 内置依赖仓库等少数地址  
- **拉沙箱镜像** 一般在 Runner 宿主机完成，不必对业务容器开放镜像仓库  
- 白名单宜可配置（全局 DAP + 按产品/对接环境），LLM 出站仍走 dap-agent，不走业务沙箱网

#### 2.3.9 阶段建议

| 阶段 | 内容 |
|---|---|
| **B0** | 产品资源池+名额；Manager 主控 + 单机 sandbox-client；从 dap-server 拆出仓读写/`run_action`（可先 docker exec）；mount worktree；commit；还名额；网络白名单 |
| **B1** | 多节点 client 注册/健康指标；本机反向代理独立 code-tools；名额对账；同资源多需求防撞 |
| **B2** | 与 IT 租约/Compose、对接环境白名单一体 |
| **B3** | 多运行时（内核隔离）适配；视需要共享盘 / K8s |

## 3. 提示词与上下文管理

### 3.1 已拍板口径

- **不做**个人用户「事实卡」类长期记忆：研发场景价值有限，隐私与治理成本高。
- **只做**会话持久化记忆（本需求 / 本单元会话）；跨会话知识沉淀靠 **Wiki 正式产物**，不靠聊天记忆。

### 3.2 现状问题

因 Agent 需要读文件，上下文容易拉得很宽。虽有 `ripgrep` 等检索降低全量读取，但缺少：

- 按任务类型的硬预算
- 材料拉取分级策略
- 提示词版本与租户覆盖治理

`ripgrep` 解决「找得到」，不解决「不该看的别进上下文」——后者仍靠材料白名单 + 预算。

### 3.3 规划要点

| 项 | 说明 |
|---|---|
| 硬预算分桶 | 系统提示 / 材料索引 / 检索片段 / 历史消息 分别设 max tokens |
| 分级拉取 | 默认路径+摘要 → search 命中 → read 片段；禁止一次塞整本 Wiki |
| 提示词运营 | 与任务类型绑定、版本化、可灰度；租户覆盖可审计 |
| 会话边界 | 仅本需求/本单元；跨会话只认 Wiki 正式文档 |

## 4. Token、超时与取消

### 4.1 缺口

目前尚未体系化做：

- 用户 / 租户 Token 配额
- 工具调用超时
- LLM 处理超时
- 取消在多实例下的可靠传播

### 4.2 规划控制面

| 控制 | 建议 |
|---|---|
| 配额 | 租户/用户日、月 Token 额度；软限告警 + 硬限拒绝 |
| 单次上限 | 单会话 / 单 Job：max input、max output、max tool rounds（与流水线 T24/T48/T96 挂钩） |
| LLM 超时 | 连接超时、首 token 超时、整段超时；超时记失败并可策略重试 |
| 工具超时 | 单工具墙钟超时；沙箱内再套一层 |
| 取消 | 用户停止 → Job / Agent / 工具链统一取消（多实例依赖外置 run 注册表） |

无配额与超时，上量后易出现账单打爆、Agent 挂死占槽。

## 6. Agent 任务水平扩容

### 6.1 问题

当前偏单机：`PipeJobWorker` 线程池、`runId` 等运行态易落在进程内；多副本下停止生成、抢 Job、SSE 粘滞都会出问题。

### 6.2 目标形态

```text
浏览器 → dap-server（无状态多副本）
            ├─ Job 队列（现有 pipe_job 可演进；可加 Redis/MQ）
            ├─ 运行态 runId / 租约（Redis）
            └─ dap-agent / Runner 多副本
文件与仓 → 共享存储，或「执行器本地盘 + 任务亲和」
```

### 6.3 要点

1. **dap-server 无状态**：JWT + 外置锁与 run 注册表  
2. **dap-agent 水平扩**：`stop` 经 Redis 定位执行节点  
3. **编码/IT 任务**：worktree 在共享盘，或调度亲和到同一 Runner  
4. **Job 集群抢占**：多实例条件更新 `PENDING → RUNNING`（已有雏形，做成集群能力）  
5. **背压**：按租户并发槽位；槽满排队，不无限起 Agent  

控制面（server）多副本 + 执行面（agent/runner）弹性池。

## 7. 集成测试并行：端口、Flyway 与运行时隔离

### 7.1 问题本质

| 已隔离 | 未隔离（冲突点） |
|---|---|
| Git 分支 + worktree | 默认固定 `server.port` |
| 流水线实例 / Job | 同一库/schema 多进程抢 Flyway |
| | 共享 Redis/MQ key、外部依赖 |
| | 测试写库互相污染 |

**worktree 只解决「改哪份代码」；集成测试还要解决「各自有一套可启动的运行时」。**

### 7.2 策略选项

| 策略 | 做法 | 适用 |
|---|---|---|
| A. 随机端口 + 独立 schema | `port=0`；每需求/每 cycle 独立 schema；Flyway 只迁本 schema | 短线可落地 |
| B. Docker 一栈一任务 | compose 短命环境，测完销毁 | 中线企业态 |
| C. 共享环境串行 | 产品级互斥锁，同时只跑 1 个 IT | 仅应急，吞吐差 |

### 7.3 Flyway 口径

- **禁止**多需求共用开发库做集成测试 migrate  
- 每个并行任务：**独立 database 或独立 schema**  
- 测试 profile 校验照常，但 history 表互不共享  

### 7.4 与流水线衔接

在 `GEN_INT_TEST` / `INT_TEST_RUN` 前增加平台编排步骤：

```text
ensure worktree（已有）
  → allocate runtime（端口/库/容器 = f(租户, 需求, cycle)）
  → 注入会话环境 / 临时配置
  → Runner 或 Agent 执行测试
  → finally 回收 runtime
  → 写《集成测试报告-r{n}.md》
```

Agent **不得自行挑选固定 8080/5432**；由平台分配。

## 8. 开发 / 测试资源租约（端口、库模式等）

### 8.1 结论

每个需求任务可申请 **资源包（租约 lease）**，使本服务运行时独立；与 worktree 同一主维度（需求），而不是给每人永久钉死一套资源。

### 8.2 粒度建议

| 粒度 | 说明 |
|---|---|
| **默认：一需求一资源包** | 与 worktree/流水线一致 |
| 同需求多人 | 共享资源包；「启动服务」另加 runtime 占用锁 |
| 每需求 × 每用户 | 最隔离，配额压力大，按需开启 |
| 流水线 IT cycle | 短租约，测完强制回收 |

个人长驻联调：显式申请 / 续租 / 释放，带过期时间。

### 8.3 租约内容示例

```text
subject     = (tenant, product, reqNo, purpose)  # purpose: DEV | PIPE_IT | …
port.http   = 池化领取或哈希落入端口段
db.schema   = it_{product}_{reqNo} 或独立 database
redis.prefix= {tenant}:{product}:{reqNo}:
compose.project = dap-{reqNo}
workdir     = 已有 worktree 路径
expiresAt / status = ACTIVE | EXPIRED | RELEASING
```

配套：**租户/产品配额**、泄漏检测、失败/取消/超时 **finally 回收**。

### 8.4 数据与 API（草案）

- 表：`dev_resource_lease` 或 `pipe_resource_lease`  
- API：申请、查询、续租、释放  
- 与会话绑定：创建/触发单元时写入环境变量或临时配置文件

## 9. 对接环境（依赖服务）

### 9.1 问题

真实项目服务很少能「独自跑通」，通常依赖用户中心、网关、MQ、下游 RPC 等。  
仅隔离本服务端口/schema 不够，还需要配置 **对接环境**。

### 9.2 三层环境模型

```text
① 本需求运行时（租约）
   - 本服务端口、本库 schema、本 worktree
   - 人开发 / 流水线 IT 真正启动的「被测服务」

② 对接环境（产品级配置，共享）
   - 用户中心、网关、消息、对象存储、下游 HTTP/RPC
   - 按「开发对接 / 测试对接 / 预发」分套，一般不按需求一人一套

③ 可选替身（Mock / Contract Stub）
   - 下游不稳定或需大规模并行时，用桩替代部分②
```

常见组合：**① 隔离 + ② 共享对接 + 必要时 ③ 替身**。

### 9.3 对接环境配置（挂在产品上）

每个产品维护若干 Environment Profile，例如：

| 字段 | 含义 |
|---|---|
| `code` | `dev-integration` / `qa-integration` |
| `baseUrls` | 网关与依赖服务地址 |
| `auth` | 测试账号、client 凭证（密钥库引用） |
| `middleware` | 共享 Redis/MQ 的逻辑前缀或专用 vhost |
| `network` | 内网/VPN、Runner 可达性 |
| `rules` | 可写范围、禁打生产、限流 |

启动时 **合并配置**：

```text
本服务 port / 本库 = 租约
依赖 URL / 测试账号 = 对接环境
→ 注入会话与 worktree，人与 Agent 共用
```

### 9.4 共享对接环境的治理

- 测试数据带需求号前缀，降低踩踏  
- 对接环境只读 / 可写分级  
- 高危写走 Mock  
- 限制同时连接对接环境的租约数  

### 9.5 集成测试两种模式（产品可配）

1. **联调模式（默认）**：起本服务（租约）→ 连对接环境 → 跑 IT  
2. **契约/沙箱模式**：本服务 + 本地/Compose stub，少依赖或零依赖对接环境  

`GEN_INT_TEST` 必须标明 profile，禁止写死「永远全链路」。

## 11. 优先序建议（企业版 MVP → 完整）

### P0 — 能安全小范围上线

1. SSO（单点登录）/ 审计 / 本岗硬权限（流水线触发·确认·发布）  
2. 密钥库（LLM / Git / Internal Token）  
3. 材料 ACL 硬化 + 任务工具画像  
4. 基础：LLM/工具超时、租户 Token 软硬配额  
5. run 级基础指标（失败、超时、token、确认次数）  

### P1 — 能多人并行开发与 IT

1. 资源租约（端口 + schema）+ 配额 + 自动回收  
2. 产品对接环境配置 + 合并注入运行配置  
3. IT：禁止共用开发库 migrate；独立 schema 或短命库  
4. Redis 外置 run 注册表；Job 多实例抢占  
5. 卡住实例运维（WAITING_HUMAN / 待发布）  

### P2 — 能规模化与强隔离

1. Docker 沙箱 Runner  
2. IT Compose/Testcontainers 一栈一任务  
3. 对象存储替代单机 data 盘；多机共享 worktree 策略  
4. 真·LLM 轨合并；集成测试对接正式 CI  
5. 完整运营看板与成本分摊  

### P3 — 平台化经营

1. Git 合主干 / PR 门禁 / worktree 生命周期自动化  
2. 推进规则完全配置化、定义版本兼容  
3. 外系统（IM/工单）与度量驾驶舱
